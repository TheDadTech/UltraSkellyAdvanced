# Bluetooth audio ownership hotfix (0.28.6 candidate)

## Established cause and evidence

USA previously provisioned two user WirePlumber sessions with both Bluetooth
monitors enabled and seat monitoring disabled. Its ownership helper stopped the
other account's entire PipeWire stack temporarily and resumed it after routing.
Consequently, USA did not maintain a single Bluetooth audio owner. Lingering and
user-manager startup made the two monitors available without an SSH session;
resuming the second monitor could reintroduce contention after a successful pair.
BlueZ bonding/connection alone does not establish a card or sink in USA's graph.

WirePlumber 0.5.8's [BlueZ monitor source](https://github.com/PipeWire/wireplumber/blob/0.5.8/src/scripts/monitors/bluez.lua#L501-L521)
creates or deactivates its monitor with the active seat when seat monitoring is
enabled; without that feature it creates the monitor directly. Its
[Bluetooth documentation](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/bluetooth.html)
describes this protection and the headless-service exception. The policy flags
are supported features, not a service-start-order ownership guarantee.

PipeWire 1.4.2's [BlueZ SPA source](https://github.com/PipeWire/pipewire/blob/1.4.2/spa/plugins/bluez5/bluez5-dbus.c)
registers media applications/endpoints on the system BlueZ bus, receives endpoint
configuration calls, and acquires transports. Those are distinct from establishing
a Bluetooth device bond. Multiple ungated monitors can register on that bus.

This establishes the USA configuration defect and a mechanism consistent with the
reported recovery. It does NOT identify which endpoint registration, profile or
transport-acquire event failed on an affected installation. No affected-device
trace was collected here. Startup timing versus actual D-Bus endpoint selection
remains a hardware investigation item; two WirePlumber processes alone do not
prove a conflict. User-facing diagnosis therefore says *possible* conflict.

## Implementation

- `audio_sessions.py` resolves the effective service UID through NSS and gives
  all USA Bluetooth playback the same session. No names, UIDs or legacy role maps
  select a second runtime owner.
- The privileged helper independently resolves systemd `User=`, accepts numeric
  user IDs, checks runtime/socket ownership, starts the user manager without an
  interactive login, and restarts only USA's WirePlumber during explicit recovery.
- Compatibility pause/resume commands no longer stop/start another account.
- If a sink is still missing, a read-only process check reports possible competing
  managers. It does not assume that every WirePlumber process owns Bluetooth.
- Repair first tries a known valid speaker bond, then restarts its own manager and
  reconnects. Discovery and bond reset are reserved for missing/unpaired targets
  or an explicit stale-authentication failure. Only the positively identified
  Classic speaker may be forgotten; BLE addresses remain excluded.
- Repair checks pairing, trust, connection, sink and default routing before success.
  A transport lost during restart is reconnected; an unresolved audio stage is a
  failure, never a pairing-success message. Offline recovery uses local commands.
- The maintenance loop restores the saved Skelly output after disconnect/restart
  without changing a system/external-output preference or resetting a bond.
- The approved UI, uploaded-media decoding and jaw timing are unchanged.

## Migration and account safety

`deploy/audio-session-policy.py` runs as the target non-root account, including
when invoked by the installer. It creates a USA owner fragment and journals prior
content in that account's `.config/wireplumber/usa-policy-recovery.json` (0600).
It does not write into user-controlled paths as root.

Only the exact legacy fragment previously generated by USA is replaced in the
installer's managed secondary account, disabling that fragment's Bluetooth
monitors. ALSA policy, PipeWire processes, other fragments and accounts are not
removed. An already-running manager under that explicitly migrated account is
restarted once to load the new fragment. Custom fragments are not overwritten;
a collision at the new owner fragment path aborts with an actionable error.
The installer does not enumerate and stop other users' services. Unknown or custom
competing monitors require the owner's explicit local review, not an automatic
machine-wide disable operation.

A root-only copy of the pre-migration audio role map is retained as
`/etc/skelly-ai/audio-sessions.before-single-owner.json` when one existed.
The service unit no longer starts a secondary user manager. Existing unrelated
lingering settings are not removed. The supported policy is for WirePlumber 0.5;
the installer refuses 0.4 before changing these policies rather than installing
configuration that 0.4 would ignore.

### Explicit reversal

Use a copy of this package's migration script, readable by the administrator, and
run it as each account that was migrated. Example identities below are fictional:

```sh
sudo runuser -u testoperator -- python3 - restore < deploy/audio-session-policy.py
sudo runuser -u secondary_test_user -- python3 - restore < deploy/audio-session-policy.py
```

The script restores exact prior content or removes the newly introduced fragment.
It refuses to overwrite policy edits made after migration. A nonexistent journal
is a no-op. Restore the previous role map from its root-only recovery copy if
reverting to the previous audio architecture. Restart only the specifically
restored managers, then use the retained application rollback if needed.

Application rollback does not automatically reverse per-user policy migration.
Versions 0.28.4/0.28.5 can read the new single-owner role map; older dual-owner
versions require explicit policy/role-map reversal. Validate rollback audio on
hardware before distribution; do not assume the old app's health endpoint proves
its Bluetooth route is usable.

## Compatibility and release gate

An existing 0.28.x SD card with WirePlumber 0.5 needs an application ZIP update
including the helper, bootstrap, unit and reversible policy migration. No new
Python dependency or reflash is required. Installation restarts USA and its audio
services and can reconnect Bluetooth; no reboot is normally required for the
managed-policy case. Custom competing policies may need targeted intervention.
The repair path needs no Internet. The existing installer still uses package
repositories; this is not a promise of a completely offline OS/package update.

Fresh-image stage sources use the same single-owner policy and provision the
managed secondary account without Bluetooth monitoring. No image was built.
An already-distributed image is unchanged until updated.

Synthetic tests cover multiple NSS accounts/UIDs, ownership authorization,
missing runtimes, two process sessions, scoped recovery, migration/reversal,
custom-file preservation, stale bonding, missing sinks, restart-disconnect,
selected-output preservation, offline operation and BLE exclusions.

Required real-Pi checks remain: 0.28.x update and reversal/rollback; WirePlumber
0.5 configuration load; cold boot and application restart with multiple lingering
accounts; paired speaker with no card; disconnect/reconnect and persisted output;
external output plus Skelly jaw mirror; audible Pi Media; and unchanged BLE control,
credentials, settings and media. Use only sanitized traces. Release is held for
these hardware checks and explicit publication approval.
